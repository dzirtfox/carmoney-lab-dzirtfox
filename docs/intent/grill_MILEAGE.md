# Grill Me: лог интервью по задаче MILEAGE

Дата: 2026-10-01. Режим Grill Me: агент не пишет intent сразу, а задаёт вопросы
по одному (не больше шести) — только те, от ответа на которые зависит
реализация. Задано 5 вопросов; вопрос про границу потребовал уточняющего
повтора — лимит не исчерпан. Следующий шаг — `intent_MILEAGE.md`.

До первого вопроса сверены `docs/setup/code_map.md` и `docs/plan/plan_MILEAGE.md`
(оба есть), ключевые факты проверены по коду: `backend/config/rules.php`,
`backend/src/Domain/DecisionEngine.php`,
`backend/src/Domain/ApplicationValidator.php`,
`backend/src/Domain/AssessmentService.php`, `frontend/app.js`.

## Что не спрашивали, потому что это видно из кода и документов

- Точка вставки: вариант Б из code_map — правило в `DecisionEngine`, порог в
  `rules.php` отдельным ключом; существующий `max_mileage_km = 500000` — граница
  валидации с другой ролью, не переиспользуется (код: `rules.php:23`,
  `ApplicationValidator.php:43-46`).
- `approved_limit` при понижении = 0 — следует из существующего тернарника
  (`AssessmentService.php:39`), отдельного решения не требует.
- Оба эндпоинта физически неразделимы — один `assess()`
  (`AssessmentService.php:28`); фронт зовёт `/api/applications` и `/api/ltv`
  (`frontend/app.js:66,69`).

## Вопросы и ответы

### 1. Граница порога: 400 000 включительно?

Спрошено: ровно 400 000 км — правило не срабатывает (решение по LTV) или уже
даёт review? Первый ответ — «нужно уточнить»; повторён с примером (LTV 50,
пробег ровно 400 000: approve или review). Ответ: **«Записать допущением»**.

Зафиксировано: допущение из `plan_MILEAGE.md` — граница включительная,
правило срабатывает при `mileage > 400000`; ровно 400 000 — решение по LTV.
**Статус: открытый вопрос — уточнить у риск-менеджмента до реализации.**

### 2. Конфликт с reject: что при пробеге 400 001 км и LTV 95?

Спрошено: решение остаётся reject или становится review?
Ответ: **«Reject остаётся reject»**.

Зафиксировано: правило понижает только `approve` → `review`; `review` и
`reject` не трогает («худшее из двух»); LTV-каскад решает первым, правило —
вторым. Закрывает вопрос №1 из `plan_MILEAGE.md`.

### 3. Что делать, если пробег не указан?

Спрошено с вариантами «оставить как есть» / «явная ошибка в валидаторе» /
«и фронт исправить». Ответ: **«Оставить как есть»**.

Зафиксировано: нет ключа / null на API → 422 «Пробег от 0 до 500000 км» (код:
`ApplicationValidator.php:43-46`), до правила не доходит; пустое поле фронта
превращается в 0 (`Number('')`, код: `frontend/app.js:14`) и проходит как
пробег 0 — существующее поведение, в этой задаче не меняются ни валидатор, ни
фронт. Закрывает вопрос №2 из `plan_MILEAGE.md`.

### 4. На какие эндпоинты действует правило?

Спрошено: оба (`/api/ltv` и `/api/applications`) или только приём заявки.
Ответ: **«Оба»**.

Зафиксировано: правило живёт в `DecisionEngine`, оба эндпоинта идут через один
`assess()` — кнопка «только расчёт» тоже начнёт возвращать review по пробегу.
Закрывает вопрос №3 из `plan_MILEAGE.md`.

### 5. Что вне scope?

Спрошено с вариантами «подтвердить список» / «добавить reason-код» /
«пересчитать старые заявки». Ответ: **«Подтверждаю список»**.

Зафиксировано вне scope: LOAN-12 (`ltv_by_age`), изменение порогов LTV и
`vehicle.max_mileage_km`, фронтенд/БД/репозиторий, пересчёт уже сохранённых
заявок, reason-коды причин review. Синхронизация `code_map.md` —
опциональный шаг после реализации. Закрывает вопросы №4–5 из `plan_MILEAGE.md`.
