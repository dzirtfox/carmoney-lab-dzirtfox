# План: правило «пробег не больше 400 000 км, иначе review» (MILEAGE)

Опирается на `docs/setup/code_map.md` (раздел «Куда встало бы правило»),
отчёт scout по пробегу из `docs/setup/AGENTS.md`, требования
`docs/spec/spec_MILEAGE.md` (REQ-MILEAGE-01…08, AC-MILEAGE-01…11) и интервью
`docs/intent/grill_MILEAGE.md`; все точки вызова `DecisionEngine`
перепроверены по коду (их четыре, см. Риски). Спека собрана по
`docs/intent/intent_MILEAGE.md` — план не выходит за её границы.

**Суть правила.** Пробег свыше 400 000 км — причина для ручного проверки:
решение `approve` понижается до `review`. Граница «не больше» включительная:
400 000 — правило не срабатывает, 400 001 — срабатывает. Граница — допущение,
требует подтверждения риск-менеджмента до реализации (intent Open questions №1,
spec REQ-MILEAGE-01/02; тесты AC-MILEAGE-01–03 фиксируют её как цель).

**Подтверждено заказчиком (интервью, `grill_MILEAGE.md`).** Правило никогда не
ослабляет решение: понижает только `approve` → `review`; `review` и `reject`
оставляет как есть («худшее из двух», вопрос 2 лога → REQ-MILEAGE-03).
Отсутствующий/null пробег — поведение без изменений (вопрос 3 →
REQ-MILEAGE-05/06). Правило действует во всех сценариях расчёта решения
(вопрос 4 → REQ-MILEAGE-04). Что именно вне scope — вопрос 5.

**Выбор места — вариант Б из code_map: внутри `DecisionEngine`.** Причины:

- code_map фиксирует свойство «`DecisionEngine` — единственное место, где
  появляется `approve` / `review` / `reject`»; вариант А (понижение в
  `AssessmentService`) нарушил бы его;
- правило относится к решению, а не к валидности заявки, — ему место рядом
  с логикой решения;
- становится юнит-тестируемым напрямую, без сборки всего конвейера.

Альтернатива А (проверка в `AssessmentService::assess()`, где пробег уже
доступен) даёт меньший дифф, но размазывает логику решения по двум классам —
отклонена.

Порог берём из конфига (конвенция «бизнес-числа не хардкодим»): новый ключ
`vehicle.review_max_mileage_km = 400000`. Существующий
`vehicle.max_mileage_km = 500000` — граница валидации с другой ролью,
переиспользовать его нельзя (code_map, раздел «Чего не хватает»).

## Тесты

Каждый кейс помечен AC из `docs/spec/spec_MILEAGE.md`, который он покрывает.

Сквозные кейсы через `AssessmentService::assess()` (фабричный payload как в
`AssessmentServiceTest::payload()`, LTV 50 — approve-зона):

- **399999 км** (AC-MILEAGE-01) → `approve`, `approved_limit` = запрошенной сумме — правило не срабатывает, решение по LTV.
- **400000 км** (AC-MILEAGE-02) → `approve` — граница «не больше 400 000» включительно, правило не срабатывает.
- **400001 км** (AC-MILEAGE-03, 07) (LTV 50) → `review`, `approved_limit` = 0 — правило понижает approve.
- **500000 км** (AC-MILEAGE-10) (LTV 50) → `review`, `approved_limit` = 0 — верхняя граница валидации, проходит валидацию и попадает под новое правило (500 000 > 400 000).
- **пустой пробег** (AC-MILEAGE-08) (нет ключа `mileage` / `mileage => null`) → `ValidationException` с ошибкой `mileage` («Пробег от 0 до 500000 км»), решение не считается вовсе, на HTTP — 422; до нового правила выполнение не доходит.

Кейсы валидации (`ApplicationValidatorTest`):

- **500001 км** (AC-MILEAGE-11) → `ValidationException` с ключом `mileage` — за верхней границей валидации, до правила не доходит.

Кейсы взаимодействия (уровень `DecisionEngineTest`, порог в `setUp()` = 400000):

- 400001 км при LTV 75 (серая зона) (AC-MILEAGE-04) → `review` — остаётся review, а не reject.
- 400001 км при LTV 95 (reject) (AC-MILEAGE-05) → `reject` — правило не ослабляет reject.
- 0 км (AC-MILEAGE-09, уровень движка) → решение строго по LTV — минимум валидации, правилом не затрагивается. Поведение пустого поля фронта (уходит как 0, код: `frontend/app.js:14`) план не меняет и отдельным тестом не покрывает — это существующее поведение без изменений (REQ-MILEAGE-06).

Покрытие сценариев REQ-MILEAGE-04 (AC-MILEAGE-06/07): оба эндпоинта
(`/api/ltv` и `/api/applications`) зовут один `assess()` (код:
`backend/src/Http/ApplicationController.php:28,59`), поэтому юнит-кейсы
`assess()` покрывают оба сценария; отдельные HTTP-тесты в проекте
отсутствуют, при желании проверить руками через `curl` (раздел Регресс).

Регресс: все существующие кейсы `DecisionEngineTest` перепрогоняются с пробегом
ниже порога (100000) с теми же ожиданиями; тесты
`testApprovesLowLtvAndSetsLimitToRequestedAmount`,
`testSendsMiddleLtvToReviewWithZeroLimit`, `testRejectsHighLtv` из
`AssessmentServiceTest` (пробег фабрики 96000) остаются зелёными без правки
ожиданий. e2e-прогона у проекта нет; HTTP-поведение (422 и новый `review` в
ответе `/api/ltv` и `/api/applications`) при желании проверить руками через
`curl`.

Все 11 AC спеки покрыты: AC-01–03, 06–07, 10 — кейсами `assess()`/`DecisionEngine`
(06–07 тем же сквозным кейсом 400001 через общий `assess()`), AC-04–05 —
`DecisionEngineTest`, AC-08 — `ApplicationValidatorTest` + `assess()`, AC-09 —
`DecisionEngineTest` (0 км), AC-11 — `ApplicationValidatorTest`.

## Риски

- **Существующая проверка `vehicle.max_mileage_km = 500000`** — это граница
  валидации («заявку вообще не принимаем», 422), а не правило решения; новый
  ключ — другое число с другой ролью. Риск перепутать: после нововведения
  диапазон 400 001–500 000 — «review-зона», а 500 001+ — по-прежнему отказ на
  этапе валидации, до `DecisionEngine` не доходит. Значение и сообщение
  `max_mileage_km` не менять.
- **Смена сигнатуры `DecisionEngine`** ломает все вызовы. По grep'у в репо их
  четыре: `AssessmentService.php:33`, `AppFactory.php:37`,
  `DecisionEngineTest.php:17`, `AssessmentServiceTest.php:27` (плюс фабричные
  payload) — все покрыты планом; внешних потребителей нет.
- **Двусмысленность «иначе решение review» снята**: прочтение «перекрывать
  любое решение» (включая `reject` → `review`, ослабление) отклонено заказчиком
  в интервью (`grill_MILEAGE.md`, вопрос 2); реализуется понижение только
  `approve` (REQ-MILEAGE-03). Остаётся открытое допущение по границе 400 000
  (см. ниже).
- **Граница 400 000 — допущение**: «включительно» (400 000 не срабатывает,
  400 001 срабатывает) не подтверждено риск-менеджментом (intent Open
  questions №1, spec REQ-MILEAGE-01/02). Если подтвердят строгую границу,
  меняются условие в `DecisionEngine` (`>=` вместо `>`) и ожидания кейсов
  AC-MILEAGE-01/02 — реализацию до подтверждения не начинать.
- **`approved_limit` при понижении** должен быть 0 — следует из существующего
  тернарника в `AssessmentService`, отдельной правки не требует, но обязано
  быть покрыто тестом (кейсы 400001 и 500000, AC-MILEAGE-03/06/07/10).
- **Правило меняет оба эндпоинта** — `/api/ltv` и `/api/applications` идут
  через один `assess()`; кнопка «только расчёт» на фронте тоже начнёт
  возвращать review по пробегу. Подтверждено заказчиком (REQ-MILEAGE-04,
  AC-MILEAGE-06/07).
- **«Пустой пробег» с фронтенда не выглядит пустым**: `Number('') = 0` в
  `frontend/app.js` → mileage 0 проходит и валидацию, и новое правило; пустым
  он бывает только на уровне API (нет ключа / null → 422). Это существующее
  поведение, план его не меняет (REQ-MILEAGE-05/06, AC-MILEAGE-08/09).
- **Seed и БД не затронуты**: 24 синтетические записи, максимум 296 000 км —
  порог не пересекают; `mileage_km INT UNSIGNED` вмещает 400 001; миграций нет.
- **Не входит**: задача LOAN-12 (`ltv_by_age`), изменение порогов LTV или
  `max_mileage_km`, правки фронтенда/БД/репозитория, пересчёт уже сохранённых
  заявок, reason-коды в API.
