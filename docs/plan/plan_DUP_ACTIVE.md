# DUP_ACTIVE: защита от повторной заявки

Учебная фича из `docs/mas/demo_source.md`: клиент не может подать вторую активную
заявку, пока предыдущая не закрыта.

## Решения человека

| # | Решение |
|---|--------|
| B1 | Активна заявка `status <> 'cancelled'`. Закрыта — `status = 'cancelled'`. |
| B2 | Продуктового механизма закрытия нет. AC-3 проверяется прямой правкой статуса в БД. |
| B3 | Автотесты без настоящей MySQL. Гарантия уникальности — на уровне БД; конкурентность человек проверяет руками. |

## Механизм

MySQL не умеет partial unique index, поэтому единственный слот на клиента держит
генерированная колонка и UNIQUE по ней:

```sql
active_ref VARCHAR(32) GENERATED ALWAYS AS (IF(status = 'cancelled', NULL, applicant_ref)) STORED,
UNIQUE KEY uq_applications_active_ref (active_ref)
```

У закрытой заявки `active_ref` = NULL, а NULL в UNIQUE не конфликтует: закрытые
заявки не мешают друг другу. Второй INSERT того же клиента получает SQLSTATE 23000
по ключу `uq_applications_active_ref`; `ApplicationRepository::save()` превращает
только эту ошибку в `DuplicateActiveApplicationException`, контроллер отдаёт
HTTP 409 с телом `{"errors":{"applicant_ref":"..."}}` — таким же JSON, какой читает
фронт (frontend/app.js).

Отвергнуто: `SELECT ... FOR UPDATE` (нужна lock-таблица, нет индекса по
`applicant_ref`), `GET_LOCK` (не транзакционно).

## Как накатывается на существующую базу

`db/schema.sql` отрабатывает только на пустом томе, поэтому на уже поднятой базе
ограничения нет, пока не выполнен шаг вручную:

```bash
make up && make migrate
```

`make migrate` — это `docker compose exec -T db mysql ... < db/migrations/002_active_application_unique.sql`.
Миграция применяется один раз; повторный запуск падает с `Duplicate column name 'active_ref'`,
и это нормально — значит, ограничение уже на месте.

Сам файл сначала показывает клиентов с двумя и более активными заявками и **сам
отказывается дальше**, если такие есть (CHECK на временной таблице, ошибка 3819
до ALTER). Удалять и переписывать заявки миграция не умеет и не должна: дубли
разбирает оператор, закрывая лишние заявки через `status = 'cancelled'`.

## Известный риск: вечная блокировка анонимного клиента

`applicant_ref` не валидируется, а контроллер подставляет фолбэк `'CL-ANON'`
(`backend/src/Http/ApplicationController.php`). Все заявки без идентификатора
клиента попадают в один слот: вторая такая заявка получит 409, и клиент будет
заблокирован до появления механизма отмены (а его нет, решение B2). То же будет,
если фронт или сторонний клиент пришлёт один и тот же `applicant_ref` дважды.

Само поле в рамках фичи не меняется: это изменило бы контракт и вышло бы за
объём задачи. Что нужно решить отдельно — валидация `applicant_ref` (обязателен
ли он) и способ разблокировки анонимных заявок. Пока это не сделано, оператору
стоит считать `CL-ANON` одним клиентом.

## Почему `hasActiveApplication()` остался

Метод не участвует в защите: `save()` отдаёт дубль по факту нарушения UNIQUE, а
предварительная проверка гонку не ловит (между проверкой и вставкой успевает
занять слот другая транзакция). Поэтому в phpdoc метода стоит запрет на
использование как pre-check.

Оставлен потому, что это единственное чтение «есть ли активная заявка у клиента»
в проекте: на нём стоят тесты хранилища (включая AC-3) и он же отвечает на вопрос
оператора по конкретному клиенту. В продукт-коде вызовов пока нет — если чтение
не понадобится, метод удаляется вместе с тестами на него.

Сгенерированная `active_ref` в API намеренно не отдаётся: в списке и карточке
заявки её нет, идентификатор клиента и статус есть.

## Проверка по AC

| AC | Чем закрыт |
|----|------------|
| 1. Первая заявка создаётся | `tests/Unit/ApplicationRepositoryActiveApplicationTest`, `tests/Unit/ApplicationControllerCreateTest`, feature-тест на MySQL |
| 2. Повторная активная → 409 | `tests/Unit/ApplicationRepositoryDuplicateDetectionTest` (разбор ошибки MySQL), `tests/Unit/ApplicationControllerCreateTest` (409 + тело), feature-тест |
| 3. После закрытия новая разрешена | `testAllowsNewApplicationAfterPreviousOneIsCancelled` в unit- и feature-тесте (закрытие прямой правкой в БД) |
| 4. Два одновременных запроса → одна активная | Автотестом не закрыт: решает уникальный ключ БД. Feature-тест проверяет инвариант «одна активная заявка», настоящую одновременность человек гоняет руками по инструкции в `db/migrations/002_active_application_unique.sql` |
| 5. Существующие тесты проходят | `make test`: 55 тестов, 5 пропущено (feature нужен настоящий MySQL) |

Feature-тест по умолчанию пропускается: он пишет в базу, включается переменной
`CARMONEY_FEATURE_DB=1`.

## Что где лежит

- `db/schema.sql` — новая схема (применяется на пустом томе).
- `db/migrations/002_active_application_unique.sql` — миграция для уже поднятой базы: `make migrate`.
- `backend/src/Domain/DuplicateActiveApplicationException.php` — доменная ошибка.
- `backend/src/Repository/ApplicationRepository.php` — разбор 23000 + `hasActiveApplication()`.
- `backend/src/Http/ApplicationController.php` — 409.
