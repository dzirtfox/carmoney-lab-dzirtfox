# CASE-02 · Скоринг заявителя и решение «одобрить / отказать / на ручную проверку»

> **Материалы кейса.** Вход для 2.5-A (intent + spec эпика) и всего дня 3.
> Все данные синтетические. Фрагменты в разделе 5 **не согласованы между собой** —
> расхождения заложены специально: их фиксируют, а не «чинят».
> Треки: **A — основной**, C.

## 1. Процесс

Анкета клиента и ответ бюро кредитных историй (синтетический аналог) поступают в
скоринговую модель. Модель возвращает балл от 0 до 1000. Балл **не пересчитывается**
командой: это чужая зона, для проекта — мок с фиксированными ответами.

Дальше работает правило перевода балла в одно из трёх решений: `одобрить`,
`отказать`, `на ручную проверку`. К каждому решению прикладывается
человекочитаемое обоснование — что именно повлияло.

Кто участвует: скоринговая модель (внешняя, мок), сервис решения (зона команды),
андеррайтер (разбирает ручные проверки), клиент (получает обоснование).

## 2. Правила

| № | Правило |
|---|---|
| П-1 | Балл **выше 700** — `одобрить`. |
| П-2 | Балл **ниже 450** — `отказать`. |
| П-3 | Балл в диапазоне 450–700 включительно — `на ручную проверку`. |
| П-4 | Балл **ровно равный порогу** (450 или 700) — всегда `на ручную проверку`, автоматическое решение не принимается. |
| П-5 | Обоснование содержит балл, применённое правило и три фактора с наибольшим вкладом. Внутренние названия признаков модели в обоснование не попадают. |

## 3. Пример входных данных

| id | Балл | Топ-факторы (из модели) | Ожидаемое решение |
|---|---|---|---|
| S-01 | 812 | стаж, доля платежа к доходу, нет просрочек | `одобрить` |
| S-02 | 700 | доля платежа к доходу, возраст, стаж | `на ручную проверку` (ровно порог) |
| S-03 | 701 | доля платежа к доходу, стаж, регион | `одобрить` |
| S-04 | 450 | просрочки 30+, число запросов в БКИ, стаж | `на ручную проверку` (ровно порог) |
| S-05 | 449 | просрочки 90+, закрытых договоров нет, стаж | `отказать` |
| S-06 | — (модель не ответила) | — | нет решения, см. пограничные случаи |

## 4. Известные пограничные случаи

- **Ровно на пороге.** 450 и 700 — по П-4 это ручная проверка. Соблазн округлить
  «в пользу клиента» велик именно здесь.
- **Балл вне диапазона** (отрицательный, больше 1000) — ответ модели считать
  некорректным; что делать дальше, в материалах не сказано.
- **Модель не ответила** (таймаут, ошибка). Решение по умолчанию не определено.
- **Факторов меньше трёх** — модель вернула один. Формат обоснования из П-5
  не выполняется.
- **Формулировка обоснования для отказа.** Внутренняя причина («высокий риск по
  сегменту») клиенту не показывается — нужен допустимый текст.

## Подсказка ведущему (участникам не показывать)

Заложенные расхождения:

1. **Поведение ровно на пороге.** Тикет требует автоматического решения на 700 и 450,
   регламент п. 4.4 — ручной проверки. Раздел 2 (П-4) следует регламенту. Это же
   ловушка кейса: агент охотно округляет «в пользу клиента».
2. **Строгое или нестрогое сравнение.** Тикет — «от 700 и выше», регламент —
   «строго выше 700». Разница в один балл и есть весь смысл П-4.
3. Дополнительно: `[DATA-score-2026Q2]` показывает, что группы «ровно на пороге»
   вели себя по-разному в разных филиалах — материал для Open questions.
